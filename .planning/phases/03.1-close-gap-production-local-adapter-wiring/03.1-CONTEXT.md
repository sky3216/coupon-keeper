# Phase 3.1: Close gap: production local adapter wiring - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 3.1 replaces the demo-only default Scan path with production local adapters before Phase 4. The app must let the user select real photos and download files/folders through platform-native system UI, run the existing on-device OCR adapter against only those selected images, persist confirmed passes in SQLite, and preserve confirmed coupon images as app-internal copies.

This phase closes the production wiring gaps recorded by the v1.0 milestone audit. It does not add Wallet list/detail UI, reminder scheduling, Pro gating, broad library scanning, background scanning, cloud processing, server sync, automatic source deletion, or new document-processing capabilities.

</domain>

<decisions>
## Implementation Decisions

### Real Photo and Download Selection

- **D-01:** The photo source path supports multi-select. Users should be able to choose several coupon images in one system picker session.
- **D-02:** The downloads/files path supports both image-file multi-select and an explicitly selected folder.
- **D-03:** The two platforms should preserve the same user intent through platform-native system UI rather than forcing identical mechanics. Android may use its system folder-selection flow. iOS should use the natural Files document-selection flow for the scope that the platform can expose reliably.
- **D-04:** When a folder is selected, process only image files directly inside that folder. Do not recurse into child folders silently.
- **D-05:** Keep the guided-scan trust boundary: the app processes only items the user explicitly selected. Do not introduce broad library access or a `scan everything` affordance.

### App-Internal Image Copies

- **D-06:** When a user confirms a pass, copy the original image bytes into app-internal storage without recompression. Barcode readability and small-text fidelity take priority over storage savings.
- **D-07:** If the same source fingerprint has already produced an app-internal image copy, reuse that existing copy instead of creating a duplicate file.
- **D-08:** App-internal copy filenames use app-generated IDs. Do not include original filenames or original paths in the copy filename.
- **D-09:** If the image copy fails, do not save the pass as complete. Show a retry path. A pass without a durable app-internal image copy must not be presented as successfully saved.

### Partial Failure and Retry

- **D-10:** If some selected items cannot be opened or OCR processing fails, continue processing the remaining items. Do not discard successful candidates because one item failed.
- **D-11:** The completion report shows the failed item count and a clear retry action. Keep the main report calm; do not show technical errors or a verbose failure list by default.
- **D-12:** Retry processes only the failed items. Do not repeat already successful items or send the user back through the system picker immediately.
- **D-13:** If failed items still remain after retry, show the remaining failure count and offer a choose-again path. The user may retry again, but the UI must not trap them in an endless retry loop.

### Existing Product Constraints Carried Forward

- **D-14:** The production default path uses on-device OCR only: iOS Vision and Android ML Kit through the existing MethodChannel boundary. No network OCR, upload, analytics of image/OCR contents, login, or cloud backup.
- **D-15:** OCR results remain review-only candidates. Confirmed saves and manual registration must preserve the existing explicit-save rule.
- **D-16:** Persist confirmed passes through a SQLite-backed `PassRepository` implementation so saved data survives app restart. Keep `InMemoryPassRepository` as the deterministic test double.
- **D-17:** Preserve fake adapters for tests and dependency injection. Replace fakes only in the production default composition path.

### the agent's Discretion

The planner and executor may choose the Flutter plugin or native-channel implementation for selected photos, files, and folders; supported image extensions; stable token construction; SQLite library and migration shape; internal directory layout; copy registry representation; generated ID format; retry state representation; and widget decomposition. These choices must preserve the user-visible decisions above and the existing `domain`, `application`, `data`, `platform`, and `presentation` layering.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `lib/platform/scan_source_picker.dart` — Existing picker contract already returns selected, cancelled, access-denied, and file-unavailable outcomes.
- `lib/domain/scan_item.dart` — Existing selected-item model separates stable fingerprint input from transient `platformSourceRef`.
- `lib/application/guided_scan_controller.dart` — Existing state machine coordinates selection, progress, duplicate skipping, cancellation, partial success, and retry entry points.
- `lib/platform/method_channel_ocr_text_recognizer.dart` — Existing Dart adapter invokes the native `coupon_keeper/ocr` channel using the transient source reference.
- `lib/platform/image_copy_store.dart` — Existing copy-store contract exposes copy, resolve, and delete operations.
- `lib/data/pass_repository.dart` — Existing repository contract provides CRUD and status-based queries that a SQLite adapter must implement.
- `lib/application/candidate_discovery_controller.dart` — Existing explicit save/manual-registration path is the point where durable copies and pass persistence must succeed together.
- `lib/presentation/screens/scan_screen.dart` — Current production composition point still injects `PhaseTwoDemoScanSourcePicker`, `FakeOcrTextRecognizer`, `FakeImageCopyStore`, and `InMemoryPassRepository`.

### Established Patterns

- Pure domain/application/data contracts stay independent of Flutter UI.
- Platform behavior sits behind interfaces, while deterministic fake adapters remain available for tests.
- Fingerprints must not include raw absolute paths.
- OCR candidates never become saved passes until the user confirms them.
- User-facing Scan copy is calm, local-only, and recovery-oriented.

### Integration Points

- Replace the default `ScanScreen` dependency composition without weakening injected-controller widget tests.
- Feed selected platform source references into the existing MethodChannel OCR recognizer.
- Add durable app-internal file copies behind `ImageCopyStore`.
- Add SQLite persistence behind `PassRepository`.
- Keep Wallet rendering and pass-detail usage in Phase 4; Phase 3.1 only makes saved data durable and ready for that phase.

</code_context>

<specifics>
## Specific Ideas

- Folder selection must feel explicit and bounded: inspect direct image children only, never child folders silently.
- Saved coupon images should prioritize reliable in-store barcode use over storage minimization.
- Partial failures should not punish successful selections. Finish useful work, summarize the failed count, and retry only failed items.
- Repeated failures should lead to a calm choose-again path rather than technical diagnostics or a forced retry loop.

</specifics>

<deferred>
## Deferred Ideas

- PDF and other document processing were not added in this discussion. Phase 3.1 stays focused on image sources; broader document support needs a separate scope decision.
- Wallet list/detail UI remains Phase 4.
- Broader library access and stronger Pro auto-scan remain a v2/Pro expansion.
- Automatic source deletion remains out of scope.

</deferred>
